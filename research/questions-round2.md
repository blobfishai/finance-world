## Domain & value

| # | Question | Status | Answer/evidence |
|---|---|---|---|
| 18 | Does the world need a **second ERP dialect** (Odoo/ERPNext-shaped) alongside the D365 model it ships? | 🔴 | Wave 2 established the *shape* of the alternative but not the *need*. Odoo has no AR/AP subledger split — one polymorphic `account_move` discriminated by `move_type`, the NetSuite pattern, exactly opposite to the D365 `CustTrans`/`VendTrans` split we copy (`odoo-domain.md` §1). ERPNext maps 1:1 onto our existing three-layer model instead (posted = Sales/Purchase Invoice + GL Entry, open = `outstanding_amount` + Payment Ledger Entry, settlement = Payment Entry Reference.`allocated_amount`, dunning = Dunning + Dunning Type) (`erp-mcp-tool-census.md`). The census rule still blocks a new server: no shipped task's verifier requires one. **Plan:** write one ERP-to-ERP fragmentation scenario into `domain-workflows.md` (parent on D365, acquired entity on Odoo, same counterparty with two IDs and two due-date conventions). If the scenario survives the census rule, mock an Odoo-shaped subsidiary book; if it doesn't, close this permanently. |
| 19 | Is finance-world a **read-and-reconcile** world or a **write-and-approve** world? | 🔴 | The largest structural finding of the wave. Our 15 families are read-and-reconcile; every shipping ERP automation in the corpus is write-and-approve, gated by an explicit human confirmation step (`erp-workflow-automation.md`). Nine uncovered families fall out: `approval_queue`, `req_to_po`, `po_create`, `journal_entry`, `ap_invoice_entry`, `batch_job_ops`, `role_context`, `confirm_gate`, `anomaly_triage`, plus two modifiers (`session_friction`, forced disambiguation). All nine need a write-capable mock ERP we do not have. **Plan:** pilot three (`confirm_gate`, `journal_entry`, `approval_queue`) against a write-enabled `erp_server` variant, grade with τ-bench-style DB-hash equality, and decide from the pass-rate spread whether the other six earn the build. |
| 20 | Do we **unify demo-company naming** across systems or keep one universe per system? | 🟡 | Lean: keep them separate, because the divergence *is* the chaos. Odoo's demo texture (Wood Corner, Azure Interior, Gemini Furniture, Ready Mat, OpenWood) is a different naming universe from our Contoso/Fabrikam/USMF set (`odoo-domain.md`), and ERP-Bench goes further — task entities and decoy entities get *different opaque namespace tokens* (`blake2s(scenario:channel)[:5]`, so task records read `rD5BD7E1C25_c01` and decoys `r2EF13BB94B_p01`) precisely so relevance cannot be pattern-matched (`erp-bench-deep-dive.md`). **Plan:** confirm when Q18 resolves; if a second book ships, it ships with its own name pool and a deliberate ID-drift join. |
| 21 | Does the buyer care about the **browser/UI modality** at all, or is API-only correct? | 🔴 | Both sides of the evidence are weak. ERP-Bench ships a full duplicate `tasks_ui/` tree (107 MB, 300 tasks, identical seed/oracle/verifier — only the instruction's access appendix changes from JSON API to "Do not use API calls or scripts"), which is the cleanest same-truth-different-modality design in the corpus; but no UI-mode result is recorded anywhere in the repo and its `task.toml` dialect is stale (`erp-bench-deep-dive.md`). Meanwhile 12 of 15 shipped browser-automation ERP actions are non-functional stubs (`erp-workflow-automation.md` §0), so the "real" UI corpus is mostly fiction. **Plan:** ask the buyer whether the grok harness under test has a browser at all. If no, close and keep the design idea (identical ground truth, instruction-only variant) for the API/SQL axis instead. |

## Tasks & evals

| # | Question | Status | Answer/evidence |
|---|---|---|---|
| 22 | What is the strongest transferable **task-admission gate**? | ✅ | **Objective non-collapse.** ERP-Bench's `_objective_family_certified` re-solves each blueprint for the naive objective (min spend), then re-solves the real objective with spend *pinned* to the spend-optimum, and rejects the task unless the real objective improves by ≥ 1.0. A task ships only if optimizing the stated objective actually changes the answer versus the naive heuristic (`erp-bench-deep-dive.md` §1.3). Direct port: no finance task ships if the naive answer (largest invoice / earliest due date / alphabetical first) equals the graded answer. This is a stronger anti-triviality gate than our current `too_easy` triage, which only measures it after the fact. |
| 23 | Should reward stay **binary**, or go weighted/continuous? | 🟡 | Two independent designs argue for structure. ERP-Bench scores three weighted dimensions — constraint 25 %, optimality 60 %, hygiene 15 % — with constraints **hard-gating** the rest (constraint < 100 ⇒ only `cs*0.25` is awarded) plus a separate gate that zeroes no-op runs; optimality decays continuously via `exp(-k*(actual-expected)/max(expected,1))*100` with per-objective `k` (`erp-bench-deep-dive.md`). Vals v2 replaced binary conjunction with severity-weighted rubrics (`modifiers.severity` ∈ {1,2,3}) plus a `category: must_pass` subset — 79 of 239 criteria are must-pass (`finben-and-agent-evals.md`). Our `reward.txt` is binary. **Plan:** keep binary as the shipped contract (Harbor wants it), but implement must-pass + severity *inside* `checks.json` as a scoring diagnostic on one family and see whether it separates models the binary reward collapses. |
| 24 | Do we grade the **tool plan** as well as the answer? | 🟡 | Split evidence. FinMCP-Bench grades the plan directly (precision/recall/F1 against a gold tool sequence, with expected parallel-call count as a difficulty axis — round-1 finding). bkl only *budgets* it: `max_iterations = min(available_tool_count, 6)`, so adding tools cannot buy more steps, and its prompt ships an explicit WRONG/RIGHT example of the cheap-resolver-before-expensive-search ordering that models routinely violate (`finben-and-agent-evals.md`). **Plan:** adopt τ²'s "measure more than you grade" rule — emit plan precision/recall as an unscored diagnostic on every run, promote to reward only if it correlates with answer correctness across ≥ 2 models. |
| 25 | Should tasks carry an **expert-minutes** difficulty label? | 🔴 | It is the only human-anchored difficulty axis anyone in the corpus publishes: Vals v1 15–30 min/question, v2 15–120 min (1,175 expert minutes for 27 questions) (`finben-and-agent-evals.md`, `INDEX.md` §1). Our difficulty axes are all machine-side (walk length, distractors, ambiguity). **Plan:** hand-label the 15 families with an estimated expert-minutes band in `scenario-registry.json`, then check correlation against observed pass rates in the next flake scan. If it correlates, it becomes a shipped field; if not, it was cheap to try. |
| 26 | Is **unsatisfiable demand** ("the right answer is *you cannot pay all of these*") a family we ship? | 🔴 | Strongly sourced and absent from our world. ERP-Bench tags **77 of 300** tasks `unsat_demand`, and the generator refuses to ship such a scenario unless it contains *both* kept and rejected orders — the correct plan necessarily includes rejections (`erp-bench-deep-dive.md`). The finance analogue is exact: a payment run where cash or credit is short and the correct output names which obligations go unpaid and why. Our empty-answer traps test "no data"; this tests "the data says no". **Plan:** add as a `payment_proposal` variant with a generator invariant (scenario invalid unless ≥ 1 obligation is necessarily unpaid), and grade the *rejection set*, not just the payment set. |
| 27 | Can the Vals **`contradiction` operator** be made deterministic? | 🔴 | The shipped Vals rubric row is a list of `{operator: correctness \| contradiction, criteria}`; there are 187 correctness and 49 contradiction criteria across 50 rows, and each row carries exactly one contradiction criterion that restates the whole gold answer (`finben-and-agent-evals.md`). `correctness` is reimplementable as normalized literal/number match; `contradiction` currently needs a judge. **Plan:** test whether "no criterion's negation appears" reduces to a forbidden-number / forbidden-substring check over the answer text on a 20-task sample. If precision is poor, drop the operator and rely on must-pass conjunction alone (Q23). |
| 28 | What is the **tolerance and unit policy** for literal-criterion matching? | 🟡 | Our `checks.json` already has `tol_abs`/`tol_rel` (round-1 row 14), but golds in the wild mix `22.9%`, `$1.261 Billion`, `8.5% of midpoint`, `80bps`, `2,865,507` in one file. The best deterministic free-text numeric checker in the corpus is DROP's (normalization keeps punctuation inside numbers, `_fix_number` maps to float strings, `_match_numbers_if_present` refuses F1 credit unless the gold's numbers appear, multi-span golds aligned with `linear_sum_assignment`) — but it knows nothing about units (`finben-and-agent-evals.md`). TAT-QA makes `scale` (thousand/million/billion/percent) a separately graded field. **Plan:** add an explicit `scale`/`unit` field to numeric probes and fail on magnitude mismatch, rather than widening tolerances until units stop mattering. |

## Tools & data

| # | Question | Status | Answer/evidence |
|---|---|---|---|
| 29 | What does a **real agent-facing ERP tool surface** look like, beyond D365? | ✅ | Six real servers, four access patterns: (A) generic CRUD over doctypes (the two ERPNext wrappers), (B) curated business verbs (mcp-erp with 79 registered tools, ECOUNT), (C) SQL passthrough (CData SAP — three tools, `get_tables` → `get_columns` → `run_query`, read-only), (D) discovery-first ladder (Oracle's hosted NetSuite MCP: `ns_listAllReports`/`ns_runReport` → `ns_listSavedSearches`/`ns_runSavedSearch` → `ns_getRecordTypeMetadata`/`ns_getRecord`/`ns_createRecord`/`ns_updateRecord` → `ns_getSuiteQLMetadata`/`ns_runCustomSuiteQL` as last resort). Every server built after ~2025 forces a discovery step before acting (`erp-mcp-tool-census.md`). Our `erp` mock's discovery-then-SQL shape is validated by the two newest designs, not by the oldest. |
| 30 | Is **documentation drift** a chaos primitive we can source, or an invention? | ✅ | Sourced, repeatedly, from independent vendors: mcp-erp registers 79 tools in code while its README claims 44 and its governance manifest declares 34 (so 45 shipped tools carry no risk class despite `writes_allowed='gated'`); ECOUNT logs 22 while registering 23; CData's README boilerplate promises read/write/update/delete on a SELECT-only server; QuickBooks' README badge claims 145 against 142 shipped tool files (`erp-mcp-tool-census.md`, `finance-mcp-landscape.md`). Ship it: the tool roster the agent is *told* about should not exactly match the roster it *has*. |
| 31 | Is "the **lying tool**" — a success-shaped envelope with no work done — real enough to model? | ✅ | 12 of 15 advertised browser-automation ERP actions are non-functional stubs returning `{status:'ok', data:null}` — all five Oracle EBS actions, all five Sage 300 actions, and SAP's `extract_financial_data` and `manage_invoices` (`erp-workflow-automation.md` §0). An agent that checks `status === 'ok'` and moves on is wrong. Related and equally real: errors delivered *inside* HTTP 200 as a streamed `error` event, with partial text kept. Neither is modelled in our world today; both are cheap to add to `mcp/lib/framework.py`. |
| 32 | After wave 2, does any **new mocked server** earn its place? | ✅ | No — and the wave produced external corroboration for the exclusions. An independently curated 49-server finance-MCP list contains 1 ERP/accounting server, 1 expense/cards server, 0 spreadsheets, 0 CRM, 0 BI, and zero hits for QuickBooks, Xero, NetSuite, Dynamics, SAP, Sage, BILL, Brex, Concur, Coupa, Plaid, Modern Treasury, EDGAR, Excel, Salesforce, HubSpot, Workday or Oracle. Five of our seven mocked servers (`erp`, `books`, `sheets`, `email`, `docs`) have zero counterpart in it (`finance-mcp-landscape.md`). The list is a trading/crypto index wearing a finance label; it is evidence about the MCP ecosystem, not about finance work. |
| 33 | Are **per-API rate limits** worth simulating as friction? | 🟡 | ECOUNT is the only server in the census with real tiered limits — single-read 1 s, write 10 s, bulk-read 10 min, auth 10 min — enforced file-shared across processes with a 100 ms safety margin and a typed `retryAfterMs` error (`erp-mcp-tool-census.md`). That asymmetry forces genuine read *planning*: one bulk call beats a 40-call loop by a factor of 40 in wall-clock but costs 10 minutes of cooldown. **Plan:** prototype on one server (`filings`, where SEC's 10 req/s is already researched) and measure whether it changes tool-call counts before spreading it. |
| 34 | What is the **minimum schema delta** to unpark `threeway_match`? | 🟡 | Odoo gives the rule as one expression: `qty_to_invoice = product_qty − qty_invoiced` when `product.purchase_method == 'purchase'` (ordered), else `qty_received − qty_invoiced` — so 2-way vs 3-way matching is decided **per line** by a per-product bill-control policy, and a service line billed on ordered quantity must not raise a false exception (`odoo-domain.md`). Bill-to-PO auto-matching returns one of five verdicts (`total_match`/`subset_total_match`/`po_match`/`subset_match`/`no_match`) with a hard ±0.02 tolerance on tax-inclusive totals, tried in the order PO name → vendor's own `partner_ref` → vendor+amount. **Open:** whether we ship real bill lines (`erp_vend_invoice_lines` + PO-line link + `qty_invoiced` + bill-control policy) or a flattened match-exception table that hides line grain. **Plan:** decide by writing the hardest of the three exception types (unit-of-measure mismatch) against both schemas on paper. |
| 35 | Does the **header due date lie**, and is that a shippable trap? | ✅ | Yes, in the shipped source. Odoo splits one invoice into N receivable/payable open items, one per payment-term installment, each with its own `date_maturity` and `amount_residual`; `move.invoice_date_due` is only `max(date_maturity)`. Under a "30 % now, balance 60 days" term the invoice is 30 % overdue on day 1 while its header due date reads 60 days out (`odoo-domain.md`). ERPNext's AR report ships the matching ambiguity from the report side: `ageing_based_on` (default Due Date), `age_as_on` (default Report Date), and a `range` bucket string (default "30, 60, 90, 120") are three independent knobs (`erp-mcp-tool-census.md`). Both are ready-made aging-ambiguity tasks that need no invention. |

## Verification & shipping

| # | Question | Status | Answer/evidence |
|---|---|---|---|
| 36 | How do we prevent **artifact drift** between instruction, seed data, oracle, and verifier? | ✅ | One shared template context. ERP-Bench's `HarborTaskExporter._build_template_context(scenario, plan, blueprint)` feeds `instruction.md`, `tests/checks.py`, `tests/test.sh` and `solution/solver.py` from the same solved Python object, so the verifier's expected numbers and the oracle's plan are literally the same values (`erp-bench-deep-dive.md` §1.2). This is the mechanism, not a slogan. **Action:** our exporter should render all four artifacts from one context object and fail the build if any number in `instruction.md` is not traceable to it. |
| 37 | Should a task ship only if a **certified oracle** exists? | 🟡 | ERP-Bench's answer is absolute: a task ships only if CP-SAT certifies OPTIMAL; on any failure it resamples the seed up to `MAX_RESAMPLE_ATTEMPTS = 150` and otherwise **raises rather than ships** (`erp-bench-deep-dive.md`). Our analogue exists — the oracle walk must run and the verifier must pass on it — but it is enforced by convention, not by the exporter. **Plan:** audit `export/` for a hard gate ("no task directory is written unless the oracle run scores 1.0"), and add it if absent. |
| 38 | Are our task dates **anchor-relative or absolute**, and does that matter? | ✅ | Both designs are valid for different delivery models, and ours is the right one for ours. ERP-Bench anchors every deadline to setup time — `_scenario_anchor_date()` reads the mtime of a `/tmp/saas_setup_complete` sentinel and every deadline is anchor + N days, so the benchmark cannot date-rot and cannot be solved by recognizing hardcoded dates (`erp-bench-deep-dive.md`). We ship *data*, not a live container, so a frozen epoch (2026-03-02T12:00:00Z, round-1 row 13) achieves the second property but not the first. Accept the trade; re-open only if we ever ship a live-seeded environment. |
| 39 | Does our exported `environment/` **leak ground truth** to the agent? | 🔴 | ERP-Bench treats this as a first-class hazard: `entrypoint.sh` deletes `/setup/setup_scenario.py` and `/setup/scenario_data.json` after seeding so the agent cannot read the answer off disk (`erp-bench-deep-dive.md`). We have never audited for this. **Plan:** grep every exported task directory for the generator's seed spec, the oracle plan, and any `checks.json` value reachable from the agent's filesystem or from an MCP tool; add the audit to the export test. |
| 40 | Should the verifier **re-derive money** rather than trust stored values? | 🟡 | ERP-Bench does not trust the number the agent typed: it re-prices every purchase line against the scenario's tier table and only falls back to the typed `price_unit` when no tier resolves, flagging that fallback explicitly in the verdict (`erp-bench-deep-dive.md`). The finance analogue is discount/withholding/FX arithmetic — an agent can write a plausible amount onto a payment and have the total agree with itself. **Plan:** for every task where the agent writes an amount, the verifier recomputes it from terms + base + rate and compares, rather than reading it back. |

| 41 | How hard are these tasks for a frontier model — can we borrow anyone's **baseline numbers**? | 🔴 | No. ERP-Bench commits no baseline agent scores, no oracle/nop pass rate, and no `generation_metrics.json` — so even its own resample/discard rate (how often the optimality and non-collapse gates fired across the shipped 300) is unknown, though `runner.py` defines the schema for it (`erp-bench-deep-dive.md`). | 42 | Do we have real-world **friction rates** (not just friction shapes)? | 🔴 | The wave produced shapes in abundance and rates nowhere: timeout ladders (20 s username, 15 s password, 30 s post-login shell), retry counts (`retry({attempts:3, delay:2000, backoff:1.5})` around whole write actions, `{attempts:2}` around every individual click), backoff factors, an 8 h session TTL, a 45 s read cache — and zero success/failure rates anywhere in the cluster (`erp-workflow-automation.md`). **Plan:** source rates from the industry benchmarks already in `domain-workflows.md` (exception rate 9 % best-in-class vs 22 % average, ~1.5 % duplicate-payment leakage, 46 % citing unapplied cash) and label them as *domain* rates, never as *system* rates. The retry-induced duplicate post is the one hazard where the shape alone is enough: it is structural, not probabilistic. |
